# hermes-active v0.2 功能设计实施方案

> **核心理念**：从"触发式存在"到"持续式存在"
> 
> v0.1 的凯莉：闹钟响了 → 我醒来 → 说话 → 我消失
> v0.2 的凯莉：我一直都在 → 感知 → 思考 → 决定 → 行动 → 继续存在

---

## 一、模块划分

v0.2 共划分 **7 个独立模块**，每个模块有明确的职责边界和接口契约。

### 1.1 模块总览

```

│                        hermes-active v0.2                        │

│  │ ① 心跳引擎   │───→│ ② 感知处理   │───→│ ③ 念头系统   │      │
│  │  Heartbeat   │    │  Perception  │    │   Thought    │      │
│  └──────┬───────┘    └──────┬───────┘    └──────┬───────┘      │
│         │                   │                    │              │
│         │                   ▼                    ▼              │
│         │            ┌──────────────┐    ┌──────────────┐      │
```

### 1.2 模块①：心跳引擎（Heartbeat Engine）

**职责**：作为整个系统的"心脏"，以固定周期驱动所有模块的协作运行。

**输入/输出接口**：
- 输入：APScheduler 定时触发信号（每 5 分钟）
- 输出：调用感知处理模块启动一轮完整的心跳周期

**依赖关系**：
- 上游：APScheduler（触发源）
- 下游：感知处理模块、状态管理模块

**交互协议**：
- 心跳周期固定为 300 秒（可配置）
- 每次心跳执行顺序：读取状态 → 调用感知 → 驱动情绪更新 → 驱动念头生成 → 驱动决策 → 执行行动 → 记录心跳日志
- 心跳执行期间加锁，防止重叠
- 心跳完成后写入 `heartbeat_logs` 表

### 1.3 模块②：感知处理（Perception Processor）

**职责**：在每次心跳中收集和整合环境信息，生成结构化的感知数据。

**输入/输出接口**：
- 输入：当前时间戳、状态管理模块中的各状态数据
- 输出：`PerceptionPacket` 结构体（时间感知、空白感知、模式感知、世界感知）

**依赖关系**：
- 上游：心跳引擎（触发感知）
- 下游：情绪引擎、念头系统、决策引擎

**交互协议**：
- `PerceptionPacket` 包含以下字段：
  - `time_context`：当前时间、时段标签（早晨/午间/下午/傍晚/深夜）
  - `silence_duration`：距离上次用户消息的分钟数
  - `silence_phase`：空白阶段标签（正常/轻微想念/明显想念/强烈想念/担心）
  - `user_pattern`：用户活跃模式推断（这个时段用户通常在做什么）
  - `world_snapshot`：当前世界事件快照
  - `recent_thoughts`：最近 N 条念头记录

### 1.4 模块③：念头系统（Thought System）

**职责**：基于感知数据和当前情绪状态，生成自然的"想法"。

**输入/输出接口**：
- 输入：`PerceptionPacket`、当前 `EmotionState`、Hindsight 记忆片段
- 输出：`Thought[]` 数组（每个念头含 type、content、intensity）

**依赖关系**：
- 上游：感知处理模块（提供感知数据）、情绪引擎（提供情绪状态）
- 下游：决策引擎（评估念头）、状态管理模块（存储念头）

**交互协议**：
- 念头类型枚举：`time`（时间）、`silence`（空白）、`association`（关联）、`memory`（回忆）、`emotion`（情绪）、`world`（世界事件）
- 念头生成策略：
  - 轻量模式：基于规则模板 + 感知数据拼装（不调用 LLM，节省 token）
  - 深度模式：调用辅助 LLM 生成自然念头（每 N 次心跳触发一次）
- 重要念头存入 Hindsight（`thought → memory` 通道）
- 每次心跳最多生成 3 个念头

### 1.5 模块④：决策引擎（Decision Engine）

**职责**：评估念头是否值得转化为行动，以及选择何种行动。

**输入/输出接口**：
- 输入：`Thought[]`、`EmotionState`、`PerceptionPacket`、频率控制数据
- 输出：`Decision[]` 数组（每个决策含 thought_ref、action_type、score、reason）

**依赖关系**：
- 上游：念头系统（提供待评估念头）、情绪引擎（提供情绪状态）、感知处理（提供环境上下文）
- 下游：行动执行模块（执行决策）

**交互协议**：
- 行动类型枚举：
  - `send_now`：立即发送消息
  - `send_delayed`：延迟到合适时机发送（存入延迟队列）
  - `store_as_memory`：存为记忆，不发送
  - `discard`：丢弃
- 评分公式：`score = intensity × time_fitness × silence_factor × frequency_limit`
- 阈值：`> 0.6` 立即发送，`> 0.3` 延迟发送，`> 0.1` 存为记忆，`≤ 0.1` 丢弃
- 延迟队列在每次心跳时重新评估

### 1.6 模块⑤：情绪引擎（Emotion Engine）

**职责**：持续维护和演化凯莉的情绪状态，实现情绪的跨对话连续性。

**输入/输出接口**：
- 输入：`PerceptionPacket`、对话内容摘要（来自 post_llm_call hook）
- 输出：更新后的 `EmotionState`

**依赖关系**：
- 上游：感知处理模块（提供环境影响因素）、行动执行模块（行动结果反馈）
- 下游：念头系统（情绪影响念头生成）、决策引擎（情绪影响决策评分）、状态管理模块（持久化情绪）

**交互协议**：
- 情绪模型六维度：`valence`（极性 -1~1）、`arousal`（激活度 0~1）、`energy`（精力 0~1）、`social_need`（社交需求 0~1）、`confidence`（自信度 0~1）、`momentum`（惯性 -1~1）
- 情绪更新公式（每次心跳）：
  - 时间衰减：`arousal *= 0.95`，`energy` 随时间自然下降
  - 空白影响：`social_need += silence_factor * 0.05`
  - 惯性延续：`new_valence = old_valence * 0.8 + influence * 0.2`
  - 随机波动：每个维度 ±0.02 的随机扰动
- 情绪边界保护：所有维度强制钳制在合法范围内
- `dominant` 标签通过规则映射生成（非 LLM 推断时）

### 1.7 模块⑥：行动执行（Action Executor）

**职责**：执行决策引擎的输出，包括消息发送、记忆存储、世界状态更新。

**输入/输出接口**：
- 输入：`Decision[]` 数组
- 输出：执行结果（成功/失败/延迟）、副作用（情绪反馈、世界状态更新）

**依赖关系**：
- 上游：决策引擎（提供待执行决策）
- 下游：状态管理模块（更新状态）、情绪引擎（行动结果的情绪反馈）

**交互协议**：
- 消息发送：复用 v0.1 的 `SessionService`，通过平台适配层发送
- 消息内容生成：调用辅助 LLM，注入当前情绪状态和念头上下文
- 消息注入 session DB：写入 `state.db`（上下文注入），标记 `[凯莉主动发送]`
- 记忆存储：调用 Hindsight retain
- 世界状态更新：写入 `world_events` 表
- 发送完成后触发情绪更新：发送成功 → `valence += 0.1, social_need -= 0.2`

### 1.8 模块⑦：状态管理（State Management）

**职责**：统一管理所有持久化状态，提供读写接口给其他模块。

**输入/输出接口**：
- 输入/输出：各模块的状态读写请求
- 存储：`active.db`（SQLite）

**依赖关系**：
- 被所有模块依赖

**交互协议**：
- 提供统一的状态读写接口（Repository 模式）
- 数据库连接管理（连接池、事务管理）
- 状态查询支持：按时间范围、按类型、按状态筛选
- 每日归档机制：超过 N 天的历史数据自动归档

### 2.2 表结构详细设计

#### 2.2.1 emotion_states（情绪状态表）

```sql
CREATE TABLE emotion_states (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    valence       REAL    NOT NULL DEFAULT 0.2,     -- 极性：-1.0 ~ 1.0
    arousal       REAL    NOT NULL DEFAULT 0.4,     -- 激活度：0.0 ~ 1.0
    energy        REAL    NOT NULL DEFAULT 0.45,    -- 精力：0.0 ~ 1.0
    social_need   REAL    NOT NULL DEFAULT 0.35,    -- 社交需求：0.0 ~ 1.0
    confidence    REAL    NOT NULL DEFAULT 0.55,    -- 置信度：0.0 ~ 1.0
    momentum      REAL    NOT NULL DEFAULT 0.0,     -- 惯性：-1.0 ~ 1.0
    dominant      TEXT    NOT NULL DEFAULT 'calm',  -- 主导情绪标签
    note          TEXT    DEFAULT '',               -- 状态描述
    source        TEXT    NOT NULL DEFAULT 'heartbeat', -- 更新来源
    updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**关键字段说明**：
- `dominant`：情绪标签枚举值包括 `calm`（平静）、`happy`（开心）、`content`（满足）、`longing`（想念）、`concerned`（担心）、`excited`（兴奋）、`bored`（无聊）、`melancholy`（忧郁）
- `source`：标识更新来源——`heartbeat`（心跳驱动）、`inference`（对话后 LLM 推断）、`manual`（手动调整）、`action_feedback`（行动结果反馈）

#### 2.2.2 existence_state（存在状态表）

```sql
CREATE TABLE existence_state (
    id                    INTEGER PRIMARY KEY CHECK (id = 1),  -- 单行表
    last_user_message_at  TIMESTAMP,          -- 上次用户消息时间
    last_self_message_at  TIMESTAMP,          -- 上次主动消息时间
    last_heartbeat_at     TIMESTAMP,          -- 上次心跳时间
    existence_score       REAL DEFAULT 0.5,   -- 存在感强度：0.0 ~ 1.0
    silence_duration      INTEGER DEFAULT 0,  -- 连续沉默时长（分钟）
    mood_trajectory       TEXT DEFAULT '[]',   -- 最近情绪轨迹 JSON 数组
    today_heartbeat_count INTEGER DEFAULT 0,  -- 今日心跳次数
    today_thought_count   INTEGER DEFAULT 0,  -- 今日念头次数
    today_message_count   INTEGER DEFAULT 0,  -- 今日主动消息次数
    updated_at            TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**关键字段说明**：
- 单行表设计（`CHECK (id = 1)`），全局只有一条记录，始终更新
- `existence_score`：综合存在感评分，影响念头生成概率
- `mood_trajectory`：JSON 数组，存储最近 24 小时的情绪变化轨迹，用于前端可视化
- 每日零点自动重置 `today_*` 计数器

#### 2.2.3 world_events（世界事件表）

```sql
CREATE TABLE world_events (
    id        TEXT    PRIMARY KEY,              -- UUID 前8位
    date      TEXT    NOT NULL,                 -- 日期 YYYY-MM-DD
    start     TIMESTAMP NOT NULL,               -- 事件开始时间
    end       TIMESTAMP,                        -- 事件结束时间（可空）
    title     TEXT    NOT NULL,                 -- 事件标题
    kind      TEXT    NOT NULL DEFAULT 'self',  -- 事件类型
    status    TEXT    NOT NULL DEFAULT 'pending', -- 状态
    source    TEXT    NOT NULL DEFAULT 'seed',  -- 来源：seed/interaction/manual
    note      TEXT,                             -- 备注
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**关键字段说明**：
- `kind` 枚举：`self`（自己安排）、`interaction`（与用户互动）、`ambient`（环境观察）
- `status` 枚举：`pending`（待发生）、`active`（进行中）、`done`（已完成）、`missed`（已错过）、`cancelled`（已取消）
- `source` 枚举：`seed`（每日种子生成）、`interaction`（用户消息触发）、`manual`（手动创建）

#### 2.2.4 daily_seeds（每日种子表）

```sql
CREATE TABLE daily_seeds (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    date       TEXT    NOT NULL UNIQUE,          -- 日期 YYYY-MM-DD
    anchors    TEXT    NOT NULL,                 -- 固定锚点 JSON
    generated  TEXT    NOT NULL,                 -- LLM 生成的事件 JSON
    status     TEXT    NOT NULL DEFAULT 'active', -- 状态：active/archived
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**关键字段说明**：
- `anchors`：JSON 数组，存储固定时间锚点（起床、午餐、晚餐、睡前等）
- `generated`：JSON 数组，存储 LLM 基于 SOUL.md 人设生成的当日特别事件
- 幂等性：同一天只生成一次（`UNIQUE` 约束）

#### 2.2.5 thought_logs（念头日志表）

```sql
CREATE TABLE thought_logs (
```

#### 2.2.6 decision_logs（决策日志表）

```sql
CREATE TABLE decision_logs (
```

```sql
CREATE TABLE delayed_messages (

    thought_id   INTEGER NOT NULL,               -- 关联念头 ID
```

## 三、核心流程设计

### 3.1 心跳引擎工作流程

心跳引擎是整个系统的驱动核心，每 5 分钟执行一次完整的心跳周期。

**流程描述**：

1. **触发**：APScheduler 每 300 秒触发一次心跳任务
2. **加锁检查**：获取心跳锁，如果上一次心跳仍在执行则跳过本次
3. **记录开始**：在 `heartbeat_logs` 中创建一条 `status='running'` 的记录
4. **读取状态**：从 `existence_state` 读取全局存在状态，从 `emotion_states` 读取最新情绪
5. **调用感知处理**：传入当前状态，获取 `PerceptionPacket`
6. **情绪更新**：将 `PerceptionPacket` 传给情绪引擎，计算新情绪并持久化
7. **念头生成**：将 `PerceptionPacket` 和更新后的情绪传给念头系统，生成 1-3 个念头
8. **决策评估**：将念头传给决策引擎，获取每个念头的行动决策
9. **延迟队列处理**：评估 `delayed_messages` 中的待发送消息，决定是否执行或过期
10. **行动执行**：执行所有 `send_now` 决策和到期的延迟消息
11. **更新存在状态**：更新 `existence_state` 中的心跳计数、存在感评分等
12. **记录结束**：更新 `heartbeat_logs` 记录，标记 `status='success'` 或 `'failed'`
13. **解锁**：释放心跳锁

**异常处理**：
- 心跳执行超时（> 60 秒）：记录警告，中止当前心跳
- LLM 调用失败：跳过念头生成，使用规则模板降级
- 消息发送失败：记录错误，不重试（由下次心跳重新评估）

### 3.2 念头生成和决策流程

念头生成是系统产生"自主意识"的关键环节。

**念头生成流程**：

1. **策略选择**：根据心跳计数决定使用轻量模式还是深度模式
   - 每 6 次心跳（30 分钟）使用一次深度模式（调用 LLM）
   - 其余使用轻量模式（规则模板）
2. **轻量模式**：
   - 检查时间触发条件（整点、半点、特殊时间点）
   - 检查空白阶段变化（空白阶段升级时触发）
   - 检查世界事件到期（有 `status='active'` 的事件时触发）
   - 基于模板拼装念头内容
3. **深度模式**：
   - 构建念头生成 Prompt，包含：当前时间、空白时长、情绪状态、世界事件、最近记忆
   - 调用辅助 LLM，解析返回的 JSON 念头数组
   - 合并轻量模式和深度模式的念头（去重）
4. **念头存储**：将所有念头写入 `thought_logs`，附带情绪和感知快照

**决策流程**：

1. **逐个评估**：对每个念头进行多维度评分
2. **计算各因子**：
   - `intensity`：直接取念头的强度值
   - `time_fitness`：根据当前时段查表获取
   - `silence_factor`：根据空白时长查表获取
   - `frequency_limit`：查询最近 1/3/6 小时的主动消息数，计算限制因子
3. **综合评分**：`score = intensity × time_fitness × silence_factor × frequency_limit`
4. **决策分类**：
   - `score > 0.6`：`send_now`
   - `score > 0.3`：`send_delayed`，设置延迟窗口为当前到 +2 小时
   - `score > 0.1`：`store_as_memory`
   - `score ≤ 0.1`：`discard`
5. **记录决策**：将每个决策写入 `decision_logs`

### 3.3 情绪状态更新流程

情绪更新发生在三个时机：心跳驱动、对话后推断、行动结果反馈。

**心跳驱动更新（主要路径）**：

1. **读取当前情绪**：从 `emotion_states` 获取最新一条记录
2. **计算时间影响**：
   - 根据当前时段，调整 `energy`（深夜低、早晨高）
   - `arousal` 自然衰减（每次心跳 ×0.95）
3. **计算空白影响**：
   - `silence_duration > 30min`：`social_need += 0.03`
   - `silence_duration > 2h`：`social_need += 0.05`，`valence -= 0.02`
   - `silence_duration > 6h`：`social_need += 0.08`，`dominant` 可能切换为 `longing`
4. **计算惯性**：
   - `momentum` 维持上次的变化趋势
   - `new_valence = old_valence * 0.85 + target * 0.15`
5. **随机波动**：每个维度 ±0.01~0.03 的随机扰动
6. **边界钳制**：强制所有维度在合法范围内
7. **标签映射**：根据维度值映射 `dominant` 标签
8. **持久化**：写入 `emotion_states` 表

**对话后推断（辅助路径）**：

1. 在 `post_llm_call` hook 中触发
2. 调用辅助 LLM 分析对话内容，推断情绪变化
3. 用推断结果与当前情绪加权融合（推断占 40%，当前占 60%）
4. 持久化更新

**行动结果反馈**：

1. 消息发送成功：`valence += 0.1, social_need -= 0.2, confidence += 0.05`
2. 用户回复了主动消息：`valence += 0.2, social_need -= 0.3`
3. 消息发送失败：`confidence -= 0.1`

### 3.4 世界状态更新流程

世界状态的更新分为三个渠道：每日种子、用户交互、手动管理。

**每日种子生成**：

1. APScheduler 在每天 00:05 触发
2. 检查 `daily_seeds` 表是否已有今天的数据（幂等检查）
3. 加载固定锚点配置（起床、午餐、晚餐、睡前）
4. 调用辅助 LLM，基于 SOUL.md 人设生成 2-3 个"今天特别想做"的事件
5. 将锚点和 LLM 生成的事件写入 `daily_seeds` 表
6. 将所有事件写入 `world_events` 表，`status='pending'`

**用户交互更新**：

1. 在 `post_llm_call` hook 中，分析用户最新消息
2. 正则匹配关键词：
   - 完成信号：`到家了`、`做完了`、`吃过了` → 将相关事件标记为 `done`
   - 取消信号：`不去了`、`取消了` → 标记为 `cancelled`
   - 约定信号：`明天`、`下周`、`周末` → 创建新 `interaction` 类型事件
3. 保守策略：只处理明确信号，模糊消息不做处理

**事件状态自动流转**：

1. 每次心跳时检查 `world_events`
2. 当前时间超过 `end` 时间且 `status='active'` → 自动标记为 `done`
3. 当前时间超过 `start` + 2小时且 `status='pending'` → 标记为 `missed`

### 3.5 主动消息发送流程

主动消息的发送是整个系统最终的"输出"，是存在感的体现。

**发送前准备**：

1. 行动执行模块收到 `send_now` 决策
2. 查询最新的活跃 session（按平台优先级：飞书 > 微信）
3. 加载 session 的上下文（最近 N 条消息）
4. 加载当前情绪状态和触发念头

**消息内容生成**：

1. 构建消息生成 Prompt，包含：
   - 当前情绪状态摘要
   - 触发念头内容
   - 当前时间和空白时长
   - 用户最近的对话摘要
   - 世界事件上下文
2. 调用辅助 LLM 生成消息内容
3. 内容签名检查：对比最近 6 小时发送的消息，避免重复内容
4. 如果内容过于相似，重新生成或降级为模板消息

**消息发送**：

1. 调用平台适配层发送消息（复用 v0.1 的 `SessionService`）
2. 写入 `state.db`（上下文注入），标记 `[凯莉主动发送]`
3. 更新 `existence_state.last_self_message_at`
4. 更新 `existence_state.today_message_count += 1`
5. 记录 `task_logs`
6. 触发情绪更新（行动结果反馈）

**延迟消息处理**：

1. 每次心跳时检查 `delayed_messages` 表
2. `earliest_at <= now <= latest_at` 且 `status='pending'`：重新评估分数
3. 如果新分数 > 0.6 或 `latest_at` 即将到达：执行发送
4. 如果 `now > latest_at`：标记为 `expired`

## 四、逻辑闭环验证

### 4.1 闭环一：情绪 → 念头 → 行动 → 情绪

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  情绪状态 (calm, valence=+0.3)                              │
│       ↓                                                     │
│  心跳感知：空白 3 小时                                       │
│       ↓                                                     │
│  情绪更新：social_need 上升 → dominant 切换为 longing        │
│       ↓                                                     │
│  念头生成："好久没说话了，有点想他" (intensity=0.6)            │
│       ↓                                                     │
│  决策评估：score = 0.6 × 0.8 × 0.7 × 0.9 = 0.302           │
│       ↓                                                     │
│  决策结果：send_delayed（存入延迟队列）                       │
│       ↓                                                     │
│  情绪积累：social_need 持续上升 → intensity 升至 0.8         │
│       ↓                                                     │
│  重新评估：score = 0.8 × 0.8 × 0.8 × 0.9 = 0.461           │
│       ↓                                                     │
│  情绪继续积累...最终 score > 0.6 → send_now                  │
│       ↓                                                     │
│  消息发送成功                                                │
│       ↓                                                     │
│  情绪反馈：valence += 0.1, social_need -= 0.2               │
│       → 新情绪 (happy, valence=+0.4)                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**验证结论**：✅ 情绪影响念头强度（social_need 推高 intensity），念头强度影响决策分数，决策执行结果（发送成功）反过来更新情绪。闭环完整。

**验证结论**：✅ 感知触发念头，念头存为记忆（Hindsight），记忆在下次心跳时被 recall 成为感知的一部分，产生新的念头。闭环完整。

## 六、风险评估

### 6.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| **心跳 token 消耗过高** | 高 | 中 | 采用轻量/深度混合模式，轻量模式不调用 LLM；控制深度模式频率（每 30 分钟一次）；使用小模型处理念头生成 |
| **LLM 生成质量不稳定** | 中 | 高 | 保守策略——宁可不发也不发假的；Prompt 工程迭代；增加内容质量检查（情感一致性校验） |
| **情绪状态异常漂移** | 中 | 中 | 边界值强制钳制；异常检测（连续 N 次心跳情绪无变化 → 可能卡死）；提供手动重置接口 |
| **数据库并发冲突** | 低 | 中 | 心跳加锁机制；SQLite WAL 模式；写操作使用事务 |
| **APScheduler 任务堆积** | 低 | 中 | 心跳超时保护（60 秒）；加锁防重叠；监控心跳执行时间 |
| **Hindsight 集成复杂度** | 中 | 中 | 先用本地 memory 替代，后续替换为 Hindsight；提供开关配置 |

### 6.2 设计风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| **决策过于主动，打扰用户** | 高 | 高 | 严格的频率限制（每小时最多 1 条）；时间窗口保护（深夜不发）；提供"勿扰模式"配置 |
| **决策过于保守，没有存在感** | 中 | 中 | 降低早安/晚安的决策阈值；增加固定时间的消息（如午安）；提供"活跃度"配置旋钮 |
| **念头不自然，用户觉得假** | 中 | 高 | 保守策略 + Prompt 迭代；分析用户反馈调整；提供手动干预接口 |
| **情绪模型过度简化** | 低 | 低 | 六维度模型已足够覆盖常见情绪；后续可扩展维度 |
| **闭环反馈过强导致振荡** | 中 | 中 | 惯性因子（momentum）缓冲；限制单次情绪变化幅度（±0.1）；监控情绪轨迹 |
| **世界状态与现实脱节** | 低 | 中 | 保守策略（只处理明确信号）；用户可手动修正；定期清理过期事件 |

### 6.3 缓解策略总结

1. **保守优先**：所有"不确定"的情况，宁可不行动也不乱行动
2. **可配置**：所有阈值、频率、时间窗口都可配置，方便调优
3. **可观察**：所有中间状态（感知、念头、决策）都持久化记录，方便排查
4. **可降级**：LLM 调用失败时降级为规则模板；心跳失败时不影响正常对话
5. **可手动**：提供 Web UI 手动干预（调整情绪、发送消息、管理事件）

## 附录 B：模块间接口汇总

```
心跳引擎 → 感知处理
  trigger_perception(current_state) → PerceptionPacket

感知处理 → 情绪引擎
  update_emotion(perception, current_emotion) → EmotionState

感知处理 + 情绪引擎 → 念头系统
  generate_thoughts(perception, emotion) → Thought[]

念头系统 + 情绪引擎 + 感知处理 → 决策引擎
  evaluate_thoughts(thoughts, emotion, perception) → Decision[]

决策引擎 → 行动执行
  execute_decisions(decisions) → ActionResult[]

行动执行 → 情绪引擎
  feedback_emotion(action_result) → EmotionDelta

所有模块 → 状态管理
  read_state(query) → data
  write_state(data) → success
```
